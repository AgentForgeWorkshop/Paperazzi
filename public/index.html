How the Searcher agent works A simple guide to what we built

One agent. A search that can adapt.

Complex research questions can need different keywords and several searches. We built a dedicated Searcher to refine queries, screen abstracts, and select relevant papers.

What makes it an agent?

The LLM chooses its next action from the results it receives. Our prompt permits query refinement when results are empty, off-topic, or insufficient; these are model judgments, not fixed branching rules.

What is inside?

Model
openai/gpt-4.1-mini through OpenRouter chooses actions.
System prompt
One set of instructions defines the task, selection rules, and when to finish.
Tools
Python functions with descriptions and input fields. These tools have no separate LLM or system prompt.
Loop & state
LangChain returns tool results to the model. Messages and retrieved, inspected, and selected papers are tracked during the run.
Execution harness
LangChain’s runtime plus our logging, validation, and limits. Up to 3 searches, 8 tool calls, and 5 model calls.
Database connection
Direct API calls through our retrieval code. MCP is not used.
How we built it: three tools + create_agent

search_literature(query)Search the selected database; return paper IDs, titles, years, and links.

inspect_sources(paper_ids)Return stored abstracts for the model to screen for relevance.

finish_search(paper_ids, note)Validate that selected IDs were retrieved and inspected, then record the selection and end the loop.

agent = create_agent(
    model=model,
    tools=[search_literature, inspect_sources, finish_search],
    system_prompt=INSTRUCTIONS,
    middleware=[LearningTrace()],
)

agent.invoke({"messages": [user_message]})

create_agent assembles the agent; invoke starts it with your query and settings. We supply the instructions, Python tools, and control code.

Scope: source discovery and abstract screening. A completed search is not a guarantee of exhaustive coverage or scientific claim verification.

Four agents, separate responsibilities Question → evidence → integrated review → evaluation

Each specialist has its own model/tool loop. Ordinary coordinator code passes structured results between them and allows one Generator revision after Judge feedback.

Searcher↓ ParserReader↓ ReviewReasonerGenerator↓ DraftJudge

Reader feedback loop: missing evidence → targeted Searcher follow-up → Reader reassessment.

Searcher agent
Choose queries, inspect abstracts, and select papers.
Reader agent
Read papers, identify essential missing evidence, request a targeted search when needed, and extract evidence-linked claims.
Generator agent
Inspect prepared claims and the relation plan, then submit and refine a cited draft.
Judge agent
Inspect cited evidence, run both original evaluation rubrics, and report revision priorities.
Tools stay separate from agents

The document parser prepares text. ReviewReasoner produces relation/action records. Neither is an agent, and a relation label is not a verification verdict.

Four initial papers, plus up to two new papers from one Reader-requested follow-up search. Available open-access full text is parsed with source locations; unavailable text is explicitly abstract-only. PDF extraction does not reconstruct tables or figures. The independent executable verification layer is not connected.
